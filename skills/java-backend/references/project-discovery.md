# 项目识别

动手前只检查与当前需求有关的目录和配置，记录以下决定会影响实现的事实：

- `pom.xml`、`build.gradle` 或 `build.gradle.kts` 中的 Java、Spring Boot、Spring Data 和测试依赖版本；使用 Maven 还是 Gradle，以及仓库提供的 wrapper。
- 启动类所在包、现有 DDD 分层与公开接口；简单项目确认根业务包，复杂项目再确认新功能所属的限界上下文。已有命名和依赖方向优先沿用。
- 持久化技术、`resources/sql/<数据库>/` 下的 Liquibase 主文件与历史 SQL、事务位置、DTO 与实体映射方式；查看同类用例。如果旧项目使用其他迁移工具，先确认已部署版本与接管方案，避免同一变更被执行两次。
- 如果使用 MyBatis-Plus，确认其版本、与 Spring Boot 对应的 starter、Mapper 扫描范围、XML 位置以及已配置的分页、乐观锁和逻辑删除行为。
- 当前已有的安全、配置、日志、指标、缓存、消息和外部客户端方案。只处理本次需求触及的组件。
- 相关测试和本地运行命令；确认是否需要外部服务，以及仓库已有的测试替身或容器配置。

缺少关键业务规则时，先在可见代码和 API 契约中寻找依据。仍无法确定的行为应向用户说明具体分歧；不要凭通用模板假定业务规则。

如果是新项目，先根据用户要求确定 Java 与 Spring Boot 版本、构建工具、数据库和运行环境，采用 Liquibase 管理数据库变更，再查对应版本的官方文档。只引入首个用例需要的组件；后续需求出现时再补充缓存、消息等集成。
