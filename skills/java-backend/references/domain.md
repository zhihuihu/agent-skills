# 领域模型

把会影响业务结果的规则写在领域对象或领域服务中，并使用项目中的业务术语命名。简单项目放在 `shop.domain`；复杂项目放在 `shop.ordering.domain` 等对应上下文的领域包，内容增长后再按聚合细分。

- **实体与值对象**：实体有持续身份；值对象由其属性定义，适合表达金额、范围、地址等概念。在 Java 17+ 项目中，推荐使用 `record` 表达不可变的值对象与领域事件。避免只有字段和 getter、把所有规则留给应用服务的贫血模型。
- **聚合**：为必须同步成立的不变量确定边界和根对象。通过根对象执行业务行为；不要因为表之间存在关联就组成一个大聚合。
- **领域服务**：规则无法自然归属单个实体或值对象时使用，保持其职责明确。
- **仓储接口**：以领域所需的操作表达读取与保存；Spring Data、SQL、缓存等实现细节放在适配层。已有项目直接使用 JPA 实体作为领域对象时，先遵循其既有边界，再避免新增持久化逻辑到业务行为中。
- **领域事件**：表达领域中已经发生的事实。是否发布为跨服务消息、如何保证投递，由应用层和基础设施决定。

创建新抽象前，确认它对应真实规则或边界。普通 CRUD 不需要为每个字段建立值对象，也不需要为每个方法建立领域服务。
