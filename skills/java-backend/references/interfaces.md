# 接口层

HTTP 控制器、消息消费者和定时任务都是用例入口。它们负责接收协议数据、校验格式、调用应用用例及返回协议结果，不承载核心业务规则。简单项目直接在 `shop` 下区分 `interapi` 和 `openapi`；复杂项目直接在对应上下文下做同样划分。自有前端及内部系统使用的 HTTP 接口放在 `interapi.controller`，向外部合作方提供的 HTTP 接口放在 `openapi.controller`，各自的请求和响应对象放在对应的 `dto` 包。没有对应接口时不创建空包。

`interapi` 和 `openapi` 是项目包名约定。`openapi` 在此表示对外入口，项目若生成 OpenAPI 规范文档，仍需单独维护接口契约。消息消费者和定时任务按调用方与用途放入对应入口包，必要时在该包内按类型细分。

- REST 请求和响应使用稳定 DTO；不要直接暴露持久化实体或跨上下文内部对象。在 Java 17+ 项目中，优先推荐使用 `record` 定义不可变的请求与响应 DTO。
- 在入口校验必填、格式和长度；项目具备 Bean Validation 支持时，优先在请求 DTO 上声明 `@NotBlank`、`@Size` 等约束，并通过 `@Valid` 触发对象校验；方法参数约束（如 `@Min`）按项目 Spring 版本的校验机制处理。避免在 Controller 方法内堆砌命令式判空校验；涉及状态与业务条件的规则由领域层保证。
- 沿用项目已有的 URL、版本、分页、错误码和响应格式约定。未有约定时，按 HTTP 语义选择状态码，并使错误信息可供调用方处理。
- 映射应用层结果和失败；优先沿用项目既有的统一异常处理。新项目可按接口契约建立 `@RestControllerAdvice`，分别核对 `interapi`、`openapi` 的错误码与响应体，并覆盖对象校验和方法参数校验异常。避免在 Controller 方法内随意 `try-catch` 包装错误体；日志保留可诊断信息，不记录凭据与敏感数据。
- 接口契约改变时同步项目已有的 OpenAPI 定义、示例或消费者测试。

消息消费者还需确认重复投递和失败重试的行为；见[消息集成](integrations/messaging.md)。
